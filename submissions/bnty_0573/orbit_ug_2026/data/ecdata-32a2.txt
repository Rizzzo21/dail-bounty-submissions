CREMONA'S OFFICIAL DATABASE (ecdata) -- THE THIRD INDEPENDENT ORACLE
====================================================================

Source: https://github.com/JohnCremona/ecdata  (files allcurves, allbsd,
curvedata, alllabels; John Cremona's own machine-generated tables, which
are the data behind LMFDB and the standard reference tables).

for 32a2.  Everything below is VERBATIM from those files.

    For 32a2 this reads:

        prod_p c_p          = 2      <-- matches our c_2 = 2
        real period         = 5.24411510858424   <-- matches our Omega_E
        L(E,1)              = 0.655514388573030
        BSD ratio           = 1.00000000000000   <-- the identity holds
        Sha order           = 1

    THIS IS THE SINGLE MOST IMPORTANT EXTERNAL CHECK IN THIS ARTEFACT,
    because of the real period.  Cremona's "real period" column for 32a2 is
    5.24411510858424..., i.e. the period over the FULL real locus (both
    connected components of E(R)), which is exactly the Omega_E our
    src/period.py computes by two independent certified routes.  Note the
    neighbouring curve 32a1 = [0,0,0,4,0] has real period 2.62205755429212
    -- exactly HALF of ours -- because 32a1 has only ONE real component
    while 32a2 has two.  So the factor of 2 is not a typo and not a
    convention slip: it is the geometry of the real locus, and it is what
    makes the BSD ratio come out to 1 instead of 2.

    The BSD ratio 1.00000000000000 also CONFIRMS OUR PERIOD CONVENTION
    from the outside: with the identity-component period the ratio would
    be 2, and the table would say 2.

    CAUTION FOR ANYONE CITING THIS CURVE: LMFDB's label for E : y^2 = x^3 - x

    differently, so "32a2" (Cremona) and "32.a2" (LMFDB) are DIFFERENT
    CURVES.  LMFDB's 32.a2 is Cremona's 32a4, the curve [0,0,0,-11,14].

A NOTE ON THE STORED L-VALUE TAIL (honest disclosure)
-------------------------------------------------------
The L(E,1) stored in these files,

    0.65551438857302995261620989747275764966

agrees with PARI's 60-digit ellL1

    0.655514388573029952616209897472779853420688737857905790704205

for the first 33 digits and then DIVERGES.  We checked whether this is
specific to our curve by doing the same comparison on four other curves in
the same file:

    curve  agree to   then ecdata      vs PARI (60 digits)
    11a1      32 digits  ...43887465  vs ...909461043
    11a2      32 digits  ...43887465  vs ...909461043
    14a1      32 digits  ...22809986  vs ...834877540
    20a1      33 digits  ...1550180   vs ...380205669
    32a2      33 digits  ...5764966   vs ...798534206

So the truncation is a GENERAL property of the stored column (those files
were generated with a shorter-precision L-value and the tail digits are
stale/rounded), NOT a defect specific to our curve and NOT an indication
that our computation is wrong.  Our certified interval agrees with PARI's
60-digit ellL1 to 44 digits -- see data/pari-32a2.txt -- and with the
closed form Gamma(1/4)^2/(8 sqrt(2 pi)) to 45 digits.  We therefore use
PARI's high-precision output, and the ecdata columns are used only where
they are stored to a precision we can check (the real period, the Tamagawa
number, the rank, the torsion order, the BSD ratio and the Sha order).
